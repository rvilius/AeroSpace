# default-window-mode patch — context

## Why this fork exists

User runs AeroSpace 0.20.3-Beta purely as a workspace-switcher: every window is
forced to floating via an `on-window-detected` catch-all rule (`'layout
floating'`). The tiling layout is never used.

**The bug:** on every new window, aerospace briefly tile-maximizes it to fill
the workspace before the catch-all callback flips it to floating. This shows
up as a visible 1–3 frame flash on app launch — most obvious on Messages, but
present for any app. Apps that don't run NSWindow autosave fast enough used
to stay stuck at maximized size until a manual resize.

User's home machine setup (cloned in this repo at `~/.config/aerospace/`,
managed by chezmoi):
- `aerospace.toml` with catch-all `run = ['layout floating', 'exec-and-forget
  snap-size']`
- `snap-size` Swift binary, runs from on-window-detected, polls AX for ~500ms
  and shrinks-on-sight
- `aerospace-watchdog` daemon, polls every 250ms, force-floats new windows
  and shrinks any window ≥0.9 ratio on both monitor axes
- Log at `~/.config/aerospace/aerospace.log`

The watchdog + snap-size approach **solved the stuck-window case** (windows
get shrunk within one poll cycle) but **cannot eliminate the flash** because:
- snap-size's binary launch + Swift runtime warmup is ~50–100ms, by which
  time aerospace has already issued the AX tile-maximize and iMessage has
  already self-restored
- watchdog runs at 4Hz, faster than that would just pile aerospace
  subprocess calls onto every cycle
- Even instant reaction wouldn't help: the tile-maximize is set as the
  window's AX frame, macOS renders the next compositor pass at that size,
  and only then do we see the size and shrink it back

## Why the in-code architecture *looks* like it shouldn't flash

Traced in upstream `main`:
- `runHeavyCompleteRefreshSession` (refresh.swift) order: `refresh()` →
  `normalizeLayoutReason()` → `layoutWorkspaces()`. The tile-resize via
  AX happens in `layoutWorkspaces`.
- `refresh()` registers the new window via `MacWindow.getOrRegister`, which
  fires `tryOnWindowDetected` (MacWindow.swift). The catch-all's
  `'layout floating'` runs there:
  - `bindAsFloatingWindow(to: workspace)` — synchronous tree move, window
    leaves the tiling container
  - `setAxFrame(nil, lastFloatingSize)` — fire-and-forget AX size restore
  - `LayoutCommand.swift` lines 47–51
- By the time `layoutWorkspaces` runs, the window is floating, so
  `layoutRecursive`'s tiling branch shouldn't touch it.

But empirically the flash happens. Likely culprits I didn't fully chase:
- `optimisticallyPreLayoutWorkspaces=true` on
  `didActivateApplicationNotification` (GlobalObserver.swift:15) runs a pre-
  layout pass — though for a brand-new window the window isn't registered
  yet, so this path is theoretical
- The fire-and-forget `setAxFrame` in the callback races against AX events
  generated by the tile-maximize that already happened (or that
  `layoutWorkspaces` does to other windows in the same tree)
- Some path I haven't read fires `setAxFrame(workspaceRect)` before the
  callback can intervene

Rather than chasing the root cause, this branch sidesteps it: don't enter
the tiling tree at all when the user explicitly says they don't want
tiling.

## The patch (branch `feat/default-window-mode`)

Adds a `default-window-mode` config option. Values: `tiling` (default,
upstream behavior) and `floating`. When `floating`, newly detected windows
are bound directly to the workspace (parent = Workspace) instead of the
root tiling container. They never enter the tiling tree, so aerospace
never sizes them to fill.

Files touched:
- `Sources/AppBundle/config/Config.swift` — `DefaultWindowMode` enum,
  `defaultWindowMode` field on `Config`
- `Sources/AppBundle/config/parseConfig.swift` — `parseDefaultWindowMode`
  parser, registration in `configParser` dict
- `Sources/AppBundle/tree/MacWindow.swift` —
  `unbindAndGetBindingDataForNewWindow`: when config says `floating`, return
  a workspace-parent BindingData for `.window`-type windows (popups and
  dialogs unchanged)

Patch is ~30 lines + comments. Designed to be upstream-able as a feature
flag — keeps existing tiling users on the default path.

## How to use it

1. Build with `./build-debug.sh` (at repo root, **not** `script/`). Needs
   `swiftly` (`brew install swiftly && swiftly init`); see `dev-docs/
   development.md`. Debug build is unsigned and doesn't need codesign.
   Produces `.debug/aerospace` (CLI) and `.debug/AeroSpaceApp` (server).
   Note the name mismatch — production server is `AeroSpace`, debug build
   is `AeroSpaceApp`. ~65s on M-series.
2. Install. The brew cask binary at `/opt/homebrew/Caskroom/aerospace/
   0.20.3-Beta/...` is codesigned and brew will revert it on next upgrade
   — don't overwrite it. Two cleaner options:
   - **Side-by-side**: kill running `AeroSpace` (PID from `pgrep -lf
     '/Applications/AeroSpace.app'`), then launch `.debug/AeroSpaceApp`
     directly. Use `.debug/aerospace` via full path for CLI, or symlink
     it ahead of `/opt/homebrew/bin/aerospace` in PATH.
   - **Replace the .app server binary in place**: `cp .debug/AeroSpaceApp
     /Applications/AeroSpace.app/Contents/MacOS/AeroSpace` (note the
     rename). Restart aerospace. Brew won't touch `/Applications` unless
     reinstalled.
   - Either way, **macOS will re-prompt for Accessibility permission**
     for the unsigned debug binary — grant it in System Settings →
     Privacy & Security → Accessibility.
3. **Order matters**: install the patched binary BEFORE `chezmoi apply`
   pushes `default-window-mode = 'floating'` to `~/.aerospace.toml` —
   the unpatched aerospace will fail to parse the new key.
4. In `~/.local/share/chezmoi/dot_aerospace.toml.tmpl`:
   - Add `default-window-mode = 'floating'` (done in current branch)
   - Optionally drop `'layout floating'` from on-window-detected callbacks
     (windows are already floating when the callback fires, so the command
     is a no-op — harmless but redundant)
   - Optionally remove `'exec-and-forget snap-size'` from callbacks (no
     window will be tile-maximized to begin with)
5. `chezmoi apply && aerospace reload-config` to pick up the new option
   without restart.
6. Verify with `aerospace list-windows --workspace Personal --format
   '%{window-id} %{app-name}'` after opening an app — should appear at its
   natural size with no flash.

## Build side effect to clean up

`swiftly init` rewrites `.swift-version` to whatever toolchain it
installed (e.g. `6.3.0` → `6.3.1`). The file is tracked. Before
committing, restore with `git checkout -- .swift-version`.

## Open questions / risks

- **Side effects of windows-never-in-tiling-tree**: aerospace might assume
  tiling-tree presence in some commands. Audit needed for: focus
  navigation, workspace move (`move-node-to-workspace`), close-window
  handling. Quick test: switch workspace, move window between workspaces,
  close window — confirm no asserts fire and the model stays consistent.
- **Interaction with `on-window-detected` matchers**: existing rules with
  `move-node-to-workspace` should still work — the move happens after the
  initial bind. Verify.
- **Dialogs and popups**: untouched by the patch. Dialogs already bind to
  workspace (floating), popups to popup container.
- **Future upstream merges**: if upstream changes `unbindAndGetBindingData
  ForNewWindow` or moves the binding logic, the patch needs to follow.
